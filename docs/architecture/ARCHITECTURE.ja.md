## サーバーは並列に何も実行しない

`server_runtime::run_until_stopped` はただひとつの `epoll`
ループでしかない。接続ごとにスレッドを立てることもなければ、
スレッドプールもない。すべての接続、すべてのデータベースクエリ、
すべての暗号処理が、ひとつのループの中を順番に通過していく。
`server/` 以下にはミューテックスがひとつも存在しない――何も並行して
動いていないのだから、守るべきものがそもそも存在しない。同じ行に
同時にアクセスする二つのリクエスト、並行書き込みで壊れるレート
リミットのカウンター――そうしたバグの一群は、起きる場所自体が
ない。その代償はスループットの上限という形で現れるが、数百万
ユーザーを抱えるサービスではなく、ひとつのコミュニティに仕える
サーバーにとって、このシングルループがボトルネックになることは
まずない。

## ソケットからフォーラムのスレッドまで

届いたメッセージは、次の順序でこれらの層を通過する:

```
TCP ソケット
  → 生バイトのバッファ(connection_socket)
  → 長さプレフィックスの除去(extract_length_prefixed_message)
  → 進行中の Noise ハンドシェイク、確立済みなら復号
  → フレームヘッダーのデコード(frame_codec)
  → レート制限(まずアドレス単位、次に本人確認済みIDの単位)
  → メッセージの種類による振り分け(request_router)
  → ハンドラー(account_handler、forum_handler、dm_handler……)
  → リポジトリ(post_repository、dm_repository……)
  → SQLite
```

最初の分岐点――ハンドシェイクかアプリケーションフレームか――は
`connection_processor.cpp` で決まる。`channel.is_established()`
が false を返している間は、届いたメッセージはすべてリクエストとして
扱われるのではなく Noise ハンドシェイクを一歩進めるために使われる。
チャネルが確立されると、以降届くものはすべて復号され、フレームとして
読み取られる。

ルーティングは、あらゆるメッセージ種別をひとつの巨大な `switch`
で処理するのではなく、いくつかのグループ(セッション、コンテンツ、
ソーシャル、DM、通報)に分かれている。これは単なる美意識の問題では
なく、プロジェクトのコーディング規約が一つの関数を六十行以内に
制限しているためだ。現時点で二十種類あまり存在するメッセージ種別を
すべて一つの switch でカバーしようとすれば、その制限を大きく
超えてしまう。`route_message` は各グループを順番に試し、どれかが
その種別を認識した時点で処理を止める。

それぞれのハンドラーは自分の仕事しか知らない――
`handle_dm_send_request` は `posts` テーブルの存在すら知らない。
共有しているのは `handler_context`(設定、ロガー、データベース
接続、クライアント接続)と、コード中で唯一 SQLite に直接触れる
リポジトリだけだ。ハンドラーが自前で SQL クエリを組み立てるように
なったら、この時点では危険信号と考えていい。

## 暗号化されたチャネル

この通信層は TLS ではない――満足させるべき Web クライアントが
存在しないし、TLS は X.509 や認証局といった、このプロジェクトには
まったく使い道のない仕組みを引きずってくる。代わりに使っているのは
libsodium の上に実装した Noise NK だ。クライアントはサーバーの
静的公開鍵をあらかじめ知っている(初回接続時にピン留めされるか、
共有された接続ファイルから読み込まれる)。なりすましのサーバーが
本物の代わりに応答しようとすれば、ハンドシェイクはただ失敗する
だけだ。

ハンドシェイクが完了すると(Noise プロトコルでこの段階を `Split`
と呼ぶ)、通信の各方向は `noise_transport` の中でそれぞれ独自の
鍵と独自の nonce カウンターを持つことになる。そのため、クライアント
からのメッセージとサーバーからのメッセージが同じ nonce を共有する
ことは絶対にない――もし共有してしまえば、ChaCha20-Poly1305 は
安全ではなくなる。この先に続くものはすべて、アプリケーション
プロトコルも含めて、両端の二台のマシン上でしか平文として存在しない。

## ひとつのクライアント、複数のサーバー

このクライアントは Slack よりも Discord に近い作りになっている:
ひとつのウィンドウ、横に並んだサーバーバー、そして各サーバーが
それぞれ自分だけのアイデンティティを保持する。もし二つのサーバー間で
アイデンティティを共有してしまえば、二人の管理者が突き合わせること
で「両方とも同一人物だ」と特定できてしまう識別子になる――この
プロジェクトはそれを避けるために、各サーバーに独自の鍵ペアを持たせ、
それらの間に目に見えるつながりを一切残さない。

状態は二つの構造体に分かれている:

- `app_state` にはアプリケーション全体に属するものが入る:
  言語設定、アクティブなスロット、セッション中だけメモリ上に
  保持され、ディスクには決して書き込まれないパスフレーズ。
- `server_slot` には*ひとつの*サーバーに属するすべてが入る:その
  接続、そのアイデンティティ、そのセッション、そして表示内容の
  ビュー状態。

スロットは値としてではなく、常に
`std::vector<std::unique_ptr<server_slot>>` の中で生きている。
理由は、うっかり壊しやすい実装上の細部にある――`client_session`
は `server_connection` とスロットのアイデンティティへの参照を
保持している。もしベクターが `server_slot` を値として保持していたら、
再確保を引き起こす `push_back` が誰にも気づかれないままそれらの
参照を無効にしてしまう。`unique_ptr` はスロットのアドレスを
永久に固定するので、サーバーを追加しても既存のスロットが動くことは
決してない。

## 何を探すならどこを見るか

| 知りたいこと | ディレクトリ |
|---|---|
| メッセージが回線上でどう構造化されているか | `common/protocol/` |
| 暗号化、鍵導出、DM | `common/crypto/` |
| ネットワークループ、レート制限、セッション | `server/net/` |
| SQLite へのアクセス | `server/db/` |
| メッセージ種別ごとのビジネスロジック | `server/handlers/` |
| 管理コマンド(ローカルソケット) | `server/admin/` |
| 接続、キーストア、マルチサーバー | `client/net/`、`client/keystore/` |
| ImGui インターフェース | `client/ui/` |
