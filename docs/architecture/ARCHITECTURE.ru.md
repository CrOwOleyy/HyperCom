между моментом, когда клиент подключается, и моментом, когда сообщение

подробностями по конкретной теме обращайтесь к другим документам:

## Сервер никогда не выполняет ничего параллельно

`server_runtime::run_until_stopped` — это единственный цикл `epoll`. Ни
потока на соединение, ни пула потоков. Каждое соединение, каждый запрос
к базе данных, каждая криптографическая операция проходят одна за
другой через один и тот же цикл, и во всём `server/` нет ни единого
мьютекса — защищать попросту нечего, поскольку ничего не выполняется
параллельно. Два запроса, обращающихся к одной и той же строке
одновременно, счётчик ограничения скорости, испорченный параллельной
записью, — вся эта категория ошибок просто не может произойти. Плата
за это — потолок максимальной пропускной способности, но для сервера,
обслуживающего одно сообщество, а не сервис с миллионами пользователей,
этот единственный цикл никогда не становится узким местом.

## От сокета до ветки форума

Входящее сообщение проходит через эти слои в следующем порядке:

```
TCP-сокет
  → буфер необработанных байтов (connection_socket)
  → удаление префикса длины (extract_length_prefixed_message)
  → рукопожатие Noise в процессе, либо расшифровка, если оно уже установлено
  → декодирование заголовка кадра (frame_codec)
  → ограничение скорости (сначала по адресу, затем по личности)
  → маршрутизация по семейству сообщений (request_router)
  → обработчик (account_handler, forum_handler, dm_handler, ...)
  → репозиторий (post_repository, dm_repository, ...)
  → SQLite
```

Первое разветвление — рукопожатие или прикладной кадр — решается в
`connection_processor.cpp`. Пока `channel.is_established()`
возвращает false, каждое входящее сообщение продвигает рукопожатие
Noise вперёд, а не обрабатывается как запрос; как только канал
установлен, всё поступающее расшифровывается и читается как кадр.

Маршрутизация разбита на семейства (сессия, контент, социальное,
личные сообщения, жалобы) вместо одного гигантского `switch` по всем
типам сообщений: правила оформления кода в проекте ограничивают
функцию шестьюдесятью строками, а switch, охватывающий два десятка с
лишним существующих типов сообщений, значительно превысил бы этот
предел. `route_message` пробует каждое семейство по очереди и
останавливается, как только одно из них распознаёт тип.

Каждый обработчик знает только свою собственную задачу —
`handle_dm_send_request` понятия не имеет о существовании таблицы
`posts`. Общее между ними — это `handler_context` (конфигурация,
логгер, соединение с базой данных, соединение с клиентом) и
репозитории, которые являются единственным местом в коде, напрямую
обращающимся к SQLite. Обработчик, самостоятельно составляющий SQL-
запрос, на этом этапе был бы тревожным сигналом.

## Зашифрованный канал

Транспорт — не TLS: здесь нет веб-клиента, которого нужно было бы
удовлетворить, а TLS тянет за собой X.509 и удостоверяющие центры, ни
одно из которых этому проекту не нужно. Вместо этого — Noise NK поверх
libsodium. Клиент заранее знает статический открытый ключ сервера
(закреплённый при первом подключении либо прочитанный из общего файла
подключения); рукопожатие попросту не удастся, если подставной сервер
попытается ответить вместо настоящего.

После завершения рукопожатия (этап, который протокол Noise называет
`Split`), каждое направление обмена получает собственный ключ и
собственный счётчик nonce внутри `noise_transport`. Поэтому сообщение
от клиента и сообщение от сервера никогда не могут использовать один и
тот же nonce — если бы это произошло, ChaCha20-Poly1305 перестал бы
быть безопасным. Всё, что происходит дальше, включая прикладной
протокол, существует в открытом виде только на двух машинах по
обоим концам соединения.

## Один клиент, много серверов

Клиент больше похож на Discord, чем на Slack: одно окно, панель
серверов сбоку, и каждый сервер сохраняет свою собственную личность.
Личность, общая для двух серверов, стала бы идентификатором, который
два администратора могли бы сопоставить, чтобы установить, что это
один и тот же человек с обеих сторон, — чего проект избегает, давая
каждому серверу собственную пару ключей без какой-либо видимой связи
между ними.

Состояние разделено между двумя структурами:

- `app_state` хранит всё, что принадлежит приложению в целом: язык,
  активный слот, пароль, хранящийся в памяти на время сессии (никогда
  не записываемый на диск).
- `server_slot` хранит всё, что принадлежит *одному* серверу: его
  соединение, его личность, его сессию и состояние отображения того,
  что на нём показывается.

Слоты живут в `std::vector<std::unique_ptr<server_slot>>`, никогда не
по значению. Причина сводится к детали реализации, которую легко
случайно сломать: `client_session` хранит ссылки на `server_connection`
и на личность слота. Если бы вектор хранил `server_slot` по значению,
`push_back`, вызывающий перевыделение памяти, незаметно сделал бы эти
ссылки недействительными — `unique_ptr` навсегда фиксирует адрес
слота, так что добавление сервера никогда не сдвигает уже
существующие.
